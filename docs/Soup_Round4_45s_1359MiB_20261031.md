**31 October 2026 | Public-data research only, no official paired jury score.** This document separates completed T4 measurements, CPU-oracle results, and unmeasured proposals. ## 2. The speed constraint

The 59.50-second candidate spent 41.42 seconds in the training loop and 18.08 seconds outside it, measured by the fixed training command. If non-loop overhead does not change, reaching 45 seconds means the loop must fall below **26.92 seconds**, a further **35.0% reduction**. A 1–2 second pointwise fusion is not enough.

The highest-priority experiment is now a profiling run of the actual CUDA operators. Only optimize whichever of quantized matrix multiplication, native SDPA, the vocabulary head or CPU synchronization dominates. Turing SM75 results from unrelated sequence lengths conflict: several small projects report both faster custom FlashAttention and much slower generic Triton FlashAttention versus PyTorch SDPA efficient. Do not assume that changing attention will speed up Qwen's 512-token task.

## 3. Quantitative memory floor

Using Qwen's published **28 layers / 1,536 hidden / 8,960 intermediate / 151,936 vocabulary / two 256-wide KV projections** with ideal 4-bit resident non-embedding weights and q/v-only rank-16 FP32 LoRA (including FP32 gradients and two Adam states):

| Resident data, optimistic | MiB |
| --- | ---: |
| 1,310,195,712 non-embedding parameters in ideal packed 4-bit | 624.75 |
| Single tied 151,936×1,536 FP16 embedding/output weight | 445.125 |
| 2,179,072 trainable q/v LoRA parameters, gradients and two FP32 Adam moments | 33.25 |
| Frozen layer RMSNorm scale vectors in FP32 | 0.33 |
| **Optimistic total** | **1,103.46** |

That excludes roughly 19.5 MiB of NF4 first-level quantized block scales and all other nested metadata, PyTorch/CUDA runtime/context, allocator, residuals, head scores, activations, and temporary workspaces. The queue's standalone T4 smoke reported 143 MiB without a model. If that size persisted, only about **112.5 MiB** would remain for metadata and all live training tensors under 1,359 MiB. This is a feasibility warning, not a theorem that the target is impossible.

A single whole-batch FP16 vocabulary logits tensor at maximum 4×512 tokens consumes **593.5 MiB**. Even a 256-row FP16 score chunk consumes **74.19 MiB** and a corresponding FP32 workspace **148.38 MiB**. Thus a winning 1,359-MiB design cannot retain whole-batch logits and probably cannot keep all packed base weights, many residuals, and even conventional 256-token head chunks resident together.

To free both weight and activation memory, consider streaming **original frozen NF4 weights** layer by layer from CPU in compressed form, fusing exact NF4 decode directly into tensor-core matmul, and selectively rematerializing activations. This keeps the model and trainable parameters unchanged but requires new ownership/event logic. The ideal packed decoder is ~624.75 MiB; one forward and one backward transfer each step over 64 steps is ~78.09 GiB before extra transfers and overlap. On the T4's PCIe Gen3×16 bus that is significant but not automatically fatal; moving ~4 GiB of activations twice per step would be a further hypothetical ~512 GiB. Neither is measured by this report. Stream concurrency and a fast decode kernel are essential.

## 4. New evidence and correction

### Head compaction: actual first GPU failure, now fixed and resubmitted

The first padded-head job **failed** at 20.557 seconds and a partial 3,039-MiB peak because its wrapper omitted the preexisting `numerics` keyword. It never completed step 1 or evaluation. This was an API bug, not a valid speed or memory result. The error was: `padded_streamed_linear_ce() got an unexpected keyword argument 'numerics'`.

A new source forwards that argument on both optimized and original fallback paths, and adds a separate finite CPU-interpreter loss/gradient preflight. It was submitted under **`chatgpt-masked-head-numerics-fix-20261031-v3`** (row 330; latest state: queued), with the unchanged solution-only training and export cells:

project-repository/blob/master/soup-kernel-challenge/queue_20261031_finite_padded_head_fixed_v2.ipynb

The masked-head mathematical oracle executed in local PyTorch CPU: **100 randomized finite cases, one 4×512 representative token case, and three adversarial guard cases passed**. It compared supervised CE, masked entropy, supervised argmax and input gradients. The adversarial guards reject (1) NaN in ignored padding, because `0×NaN` must remain NaN in native masked entropy; (2) possible FP16 overflow; and (3) an all-ignored batch, whose denominator must not silently become finite. These are **CPU component proofs**, not T4 equivalence or hidden quality guarantees.

Source oracle: `padded_head_exception_oracle.py`, output `padded_head_exception_oracle_result.json`.

### Real CUDA hotspot profiler

A separate notebook was accepted under **`chatgpt-postrun-gpu-hotspots-20261031-v1`** (row 320; latest state: queued):

project-repository/blob/master/soup-kernel-challenge/queue_20261031_postrun_24step_t4_profile_v1.ipynb

It preserves the original 60.24-second solution-only run, then profiles 24 public-data steps **after** the measured result is written and exported, in a distinct child process, with isolated Triton/Inductor caches and a separate adapter output directory. Reported profiler timings will not be represented as the measured 64-step contest time. Its purpose is to rank actual CUDA hotspots and show whether further custom attention is warranted.

### Other relevant results

- 1-GiB decoded-weight cache plus MLP compaction: 62.77 seconds / 6,721 MiB and independent repeat 62.90 seconds / 6,721 MiB. The later 1-GiB valid-row norm variant: 62.82 seconds / 6,381 MiB.
- An exact saved-activation synchronous CPU offload trial reached 3,607 MiB while running, but the process hit the 80-second cutoff **without evaluation**. Do not claim that peak as a completed result.
- Two attempts to run 79 official regressions through the queue notebook reported failure; at least one explicit preflight failure was `No module named pytest` in that service image. A failed notebook should not be silently reinterpreted as an implementation regression without reading the test log. Full Kaggle-side 79-regression verification is still necessary.

## 5. Prioritized technical next steps

1. **Read the actual profiled CUDA operator table.** If attention is already using PyTorch efficient SDPA, do not replace it with an unmeasured generic Triton FlashAttention. Prioritize measured heavy matmuls and non-loop initialization overhead.
2. **Validate native-equivalent output-head compaction.** Require full 64-step eval loss, all Soup metrics/Rewind rows, finite and nonfinite edge cases, and independent source/count attribution; only then test it with the speed and memory frontiers.
3. **Prototype an original fused NF4→FP16/Turing MMA kernel.** Keep packed bytes and nested scale/codebook metadata, and decode inside shared-memory tiles for `mma.sync.m16n8k8` without persistent FP16 matrices. Test exact weight decoding, first/last nibble, block/tail boundaries, signed zeros, scale-rounding, forward output, dX and AMP/LoRA gradients on SM75 before whole training. Do not copy external kernels or import prohibited optimization libraries.
4. **Profile resident allocation and lifetime by layer** on actual task shapes. Test custom pinned-CPU placement/prefetch only for data that cannot be cheaply recomputed, with correct CUDA events and no hidden state changes. The previous synchronous offload trial is a speed warning.
5. **Run the true ten official admission checks and paired baseline/solution on Kaggle.** A saved-baseline development badge is insufficient. In particular, original useful `@triton.jit` kernels must account for ≥5% of the timed loop from step 3 onward; starter SwiGLU time is excluded.
