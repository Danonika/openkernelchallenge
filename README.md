# Duo — Soup Kernel Challenge

Команда Duo оптимизирует фиксированное LoRA-обучение Qwen2.5-1.5B-Instruct на одной бесплатной Kaggle T4: сокращает объём сохранённых активаций и число запусков GPU-операций, сохраняя данные, параметры обучения, адаптер и выходы Soup.

В проверенной сессии Kaggle T4 полная команда занимает **46,78 с вместо 84,69 с — ускорение 1,8104×**; пик GPU **2263 MiB вместо 14345 MiB — сокращение в 6,3389×**. Eval loss отличается на **+0,009%**, все **10/10 автоматических проверок**, включая 79 тестов Soup, пройдены. Минимальная полезная доля собственных ядер — **9,2018%**. [Сохранённый проверочный запуск: Kaggle, версия 32](https://example.invalid/redacted). Это предварительный автоматический допуск; окончательное решение принимает жюри.

Выбрана реализация `adaptive448-head-vchunk4096-N1024-v1`, ранее показавшая **38,123 с / 2261 MiB / eval loss 2,04979** в одиночном исследовательском запуске. 38,123 с не выдаётся за итог новой парной сессии.

## Реализация

Точка входа — `solution.apply()`. Все вычислительные изменения находятся в `solution/`; `harness/`, `tests/` и `task/` совпадают с текущим официальным starter `c7c2fcd15972ce8b898d8d3ff732ee192c817ceb`.

| Компонент | Как работает и что экономит |
|---|---|
| Голова и метрики | Vocabulary-sliced logits, онлайн-статистики softmax и аккумулятор hidden-gradient вместо полного тензора logits. Loss, entropy, accuracy и Rewind сохраняются; все 151936 столбцов словаря обрабатываются. Градиентный GEMM использует только размеченные строки. |
| Workspace головы | При N >= 1024 рабочий срез равен 4096 вместо 8192 столбцов. Меняется размер временного буфера, а не словарь или знаменатель softmax. |
| NF4 и проекции | Общая double-quant NF4-деквантизация семи проекций слоя; у границы пика памяти — раздельный путь. Исходный формат NF4 и его значения сохраняются, дополнительной квантовки нет. QKV используют объединённые native GEMM. |
| RMSNorm и RoPE | Residual-add объединён с нормализацией; q/k rotary обрабатываются одной операцией. HALF-состояния уменьшают сохранённые активации и лишние приведения dtype. |
| MLP | При N > 448 сохраняется вход, gate/up пересчитываются в backward. Эти native GEMM и стартовый SwiGLU не заявляются собственными Triton-ядрами. |
| Padding и LoRA | Удаляются pad-токены только внутри исходного батча, с сохранением границ примеров и positions. LoRA воспроизводит dropout в backward и переиспользует HALF-копии адаптеров внутри шага. |
| Старт и host | Сокращаются повторные импорты и учёт Trainer, метрики читаются при логировании с прежними значениями. Компиляция в потоке того же процесса входит в измеряемую команду; заранее скомпилированных и межзапусковых кешей нет. |

Фиксированная нагрузка: Soup 0.77.0; Qwen2.5-1.5B-Instruct; NF4 с double quantization; LoRA r=16, alpha=32 на q_proj/v_proj с исходным dropout; batch 4; max length 512; 256 казахских инструкций; 64 шага; одна T4, fp16. Данные, порядок батчей, оптимизатор, scheduler и выходы Soup не изменяются. Режимы ускорения Soup не переключаются.

## Собственные ядра и источники

В стандартном пути работают `fused_head_vocab_kernel`, `nf4_group_dequant_kernel`, `rmsnorm_kernel` и `rope_kernel`. Ещё три JIT-функции обслуживают запасные и опциональные пути. Официальная полезная доля определяется реальными CUDA events с третьего шага отдельно в каждом solution-run; требуется не менее 5% в худшем запуске. Стартовые `example_swiglu_fwd_kernel` и `example_swiglu_bwd_kernel` исключены из собственного вклада.

Код — работа команды Duo. История основы сохранена в [Eeoneget, ce62d67432ad8e530abff12bb36d3ab15668502a](https://github.com/Eeoneget/hackathon-decentrathon-6/tree/ce62d67432ad8e530abff12bb36d3ab15668502a); поверх неё добавлены input-only MLP replay и ограничение workspace для длинного батча. Полная привязка файлов, авторства и исходных артефактов — в [docs/PROVENANCE.md](docs/PROVENANCE.md) и [docs/source-manifest.json](docs/source-manifest.json). Состав команды заполняется в SUBMISSION подтверждёнными именами, максимум четыре участника.

Стартовый проект: [MakazhanAlpamys/soup-kernel-challenge](https://github.com/MakazhanAlpamys/soup-kernel-challenge); его LICENSE и NOTICE сохранены. Источники идей: [online softmax normalizer](https://arxiv.org/abs/1805.02867), [QLoRA / NF4](https://arxiv.org/abs/2305.14314), [LoRA](https://arxiv.org/abs/2106.09685), [RoPE](https://arxiv.org/abs/2104.09864). Готовые kernel-библиотеки не используются.

## Как запустить

Репозиторий команды: [BAITC-Hacks/hack-57faaa42-duo](https://example.invalid/redacted).

Финальный commit: **`FINAL_COMMIT_PENDING`**. Финальная публичная Kaggle-версия с этим COMMIT: **`SAVED_KAGGLE_VERSION_PENDING`**. Эти два поля должны быть заполнены перед окончательной отправкой.

В `notebooks/Soup-Team-Final-Pinned-Commit-Template-v2.ipynb` уже указан URL команды и ожидаемые SHA точного пакета. Установить реальный полный Git SHA в COMMIT, выбрать Kaggle GPU T4 x2, Internet on и нажать Run All. Notebook намеренно отказывается запускаться с пустым или некорректным COMMIT. Харнесс использует одну карту через `CUDA_VISIBLE_DEVICES=0`; другая GPU-работа одновременно не запускается. Исходный официальный шаблон сохранён в `templates/kaggle_notebook.ipynb`.

На подготовленной Kaggle T4:

```bash
python -m pip install -r requirements.txt
python task/prepare_data.py
python harness/run_task.py --repeats 2 --timeout 900
python harness/check_rules.py
python harness/score.py runs/result.json
```

Все результаты находятся в **`runs/result.json`**, **`runs/checks.json`**, `runs/<run>/train.log` и `runs/eval_*.log`. `check_rules.py` самостоятельно запускает 79 регрессионных тестов с `solution.apply()`; `--skip-tests` не используется.

Замер — полное время команды от старта до сохранения адаптера, включая загрузку, компиляцию и завершение процесса. Перед каждым запуском — свежие compiler cache; порядок — база, решение, решение, база. Память снимается внешним `nvidia-smi` каждые 100 мс. Харнесс показывает медиану двух времён и максимальный пик памяти; для двух значений медиана совпадает со средним.

## Ограничения и следующие шаги

Кандидат настроен для T4 / fp16. HALF-состояния, порядок редукций и форма dropout после разрешённого внутрибатчевого unpadding могут дать небольшие численные различия при исходном seed и значении dropout. Проверяются все шаги, токены, entropy, accuracy, Rewind и единый eval; требуется первый loss в пределах 1%, средняя кривая и метрики в пределах 3%, eval loss не хуже +0,5% к базе.

Публичные строки и один seed не доказывают результат на скрытых данных. Полезная доля каждого ядра подтверждается измеряемой работой обучения, а не прогревом компиляции. Поток компиляции, C launcher -O0, патчи импорта и отложенное чтение метрик описываются открыто; исходные allocator и измеритель памяти не меняются. Автоматические проверки предварительные, окончательный допуск определяет жюри.

Для окончательной сдачи остаются: закрепить репозиторный пакет реальным финальным commit и выполнить финальный публичный Run All с тем же COMMIT, заполнить состав команды и ссылки на видео до трёх минут и презентацию. Доступ жюри к репозиторию должен быть обеспечен публичностью или через платформу. Баллы зависят от лучших допущенных команд и заранее не заявляются.
